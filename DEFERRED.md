# Deferred

Work that was consciously postponed, with the reason. Items move out of here when they are built.

| Item | From | Reason / plan |
|---|---|---|
| Trusted reverse proxies (`X-Forwarded-For`) | Phase 0 | Proxy headers are ignored so nobody can spoof a local address. Behind a proxy all clients share the proxy's address: local-address bypass then applies to everyone (or no one) and the login limiter counts them together. Add a trusted-proxy CIDR setting before the Unraid CA release (Phase 6). |
| URL base (serving under `/bunkarr`) and an external URL | Phase 0 | Not in the spec; common in *arr setups behind a proxy. Add with the trusted-proxy setting. The external URL also turns on the "Details" link to the job in notifications (the dispatcher supports it; nothing sets it yet). |
| Built-in TLS | Phase 0 | Use a reverse proxy; the session cookie is marked `Secure` when `X-Forwarded-Proto: https`. |
| First-run setup token | Phase 0 | Like the *arrs, whoever reaches a fresh instance first can create the login. Mitigation today: bring the container up on a trusted network and complete setup immediately (the log warns while no user exists). A one-time setup token printed to the log is an option if this is judged too weak. |
| Playwright smoke test (login → add destination → sync) and phone-width check | Phase 0 | Still to add. The flow is covered end to end through the API by `internal/e2e` and in the UI by component tests plus a manual pass against the real server; a browser test needs a browser in CI. The same test should check the §10 phone layout (drawer navigation, no sideways scroll at 375 px), which has no automated check. |
| Webhook endpoints `/api/v1/webhook/{sonarr,radarr,lidarr}` | Phase 0 | Phase 2 deliverable. |
| `/metrics` (Prometheus) | Phase 0 | Phase 6 deliverable. |
| Image signing (cosign), SBOM publication, dependency scanning beyond govulncheck/npm audit | Phase 0 | Phase 6 deliverable. The release workflow already attaches BuildKit SBOM and provenance attestations. |
| Sanitizing export: gitleaks secret scan | Phase 0 | The private→public sync scans for private terms (LAN addresses, account names, home paths) but not for high-entropy secrets yet. |
| Temp files of a job failed by the crash limit | Phase 1 | What such a job moved into retention is now settled by the next sync, verify or retention job (retention intents and reconciliation, design §4.2), and so are the temp files of its items when the job has a retention directory. A crash-limited job that never moved anything into retention can still leave a `.bunkarr-tmp-*` file of a copy item (space only; the name is reserved and never taken for a backup). Plan: sweep the temp paths recorded in the pending items of every failed or cancelled job. |
| Stats across a resume | Phase 1 | A resumed sync counts only its own attempt's displacements, outcome changes (a link or move that became a copy, a copy that adopted) and scan warnings, so it can end `completed` where the uninterrupted job would have warned; a resumed verify counts an earlier attempt's unreadable files as missing. Needs the ItemStore to aggregate item details (not in the jobs contract). |
| Redaction of overlapping secrets | Phase 1 | Registered secret values are replaced longest first. Two secrets that overlap in a text (the end of one is the start of the other) leave part of one visible. Fix: find all match intervals, merge them, replace in one pass. |
| Hardlinks across sources | Phase 1 | Hardlink groups are per source: two sources that share inodes (`/data/torrents` and `/data/media` as separate sources) copy the content once per source. Use one source over the common parent. |
| Accepting an empty source | Phase 1 | A source whose files were all deleted on purpose is refused ("contains no files") until a file exists or the source is recreated. An explicit "accept empty" action is to add. |
| Directory symlinks planted inside a destination | Phase 1 | `os.Root` follows a symlink that stays inside the target, so a planted directory symlink could send files to another folder of the same destination (never outside it, never over a file). A filecopy-level check is to add if that matters. |
| Bounded-memory scanning and planning | Phase 1 | A scan keeps new and changed rows in memory until its walk ends (about 150 B per file) and the planner holds a source's catalog rows and records (about 200 B per file). Fine up to a few hundred thousand files per source; multi-million-file sources need a spill file and a streaming merge-join planner. |
| Scan write volume and commit progress | Phase 1 | Every scan rewrites `last_seen_at` of every file (about 150 MB of WAL per scan for 1M files); throttle it if it matters. Only the walk reports progress, not the (faster) batched writes after it. |
| Catalog columns `hash`, `media_ids`, `arr_item_id`, `tier` | Phase 1 | Not written in Phase 1; source hashes, *arr ids and tiers arrive with Phases 2–3. |
| Type check of `plexIntegrationId` / `arrIntegrationId` | Phase 1 | The catalog may not import integrations; only the foreign key's existence is checked. |
| Unicode normalization (NFC/NFD) in collision checks; probing control characters and invalid UTF-8 | Phase 1 | Needs `golang.org/x/text`; NFS/SMB-to-Linux destinations (the Phase 1 target) do not normalize. Names the share rejects still fail per item at copy time (S11). |
| Share tests beyond Samba and Linux NFS | Phase 1 | `make test-shares` runs the sync and kill tests on a Samba share over CIFS (Unassigned Devices' options: `nounix`, `noserverino`) and on the Linux kernel NFS server over NFSv4. Not covered: a real UniFi UNAS (its own SMB/NFS servers), SMB with POSIX extensions or `mapposix`, and the mass-change guard and dry-run tests on a share (they run on local disks). Directory fsync on CIFS/NFS is taken as the filesystem provides it (EINVAL/ENOTSUP accepted). Plan: a manual pass against a UNAS before the first tagged release. |
| Platforms other than Linux | Phase 1 | Platform files exist for Linux and macOS (development only); the project is Unix-only already. |
| Bandwidth limiting | Phase 1 | Phase 4. `CopyOptions.WrapWriter` is the hook. |
| Plex servers on Windows | Phase 1 | Path settings and mappings accept POSIX paths only; drive letters need their own rules (separators, case). |
| Interrupting a Plex DB backup mid-copy | Phase 1 | SQLite's backup step cannot be stopped once started; a cancel waits for it (about 2 minutes for 5 GB) and a shutdown past the 20 s grace re-queues the job, which starts over. |
| Pruning Plex DB versions of a deleted integration; deleting versions by hand | Phase 1 | Backups are never deleted implicitly, and §7 has no snapshot delete or prune endpoint. |
| Restore UI and API | Phase 1 | Phase 5. Restore is a documented manual procedure (README, ADR 0005); the snapshots dialog lists versions and manifests. |
| Stale Plex backup destination after a crash during a destination delete | Phase 1 | Start-up removes the orphan schedule, but the integration keeps the old `destinationId` until it is saved again; a manual backup then fails with "destination not found". Normal deletes clear it. |
| Catch-up of schedules missed while Bunkarr was down | Phase 1 | Standard cron semantics: a late wake fires once and continues from now. A catch-up policy (e.g. run a missed retention at start) can be added. |
| Heartbeat independent of progress | Phase 1 | `heartbeat_at` is written with progress, so a runner silent for long (a Plex `Step(-1)`) has a stale heartbeat. Informational only: crash detection uses the instance lock and start-up recovery. |
| Settings API for `jobs.workers` and `jobs.historyDays` | Phase 1 | Not in §7. Both are read from the settings table (workers at start-up, history days by each retention run), defaults 2 and 90. |
| Apprise `tag` and body `format` | Phase 1 | §7 sends only `{urls, title, body, type}`; Apprise defaults to text. |
| Notification kinds other than Apprise | Phase 1 | The schema allows only `apprise` in Phase 1. |
| Notification bursts and delivery across restarts | Phase 1 | The in-memory queue (100) drops with a log line when full; there is no coalescing of many failures into one message, and a failed or pending delivery is not retried after a restart. |
| Apprise config key as a secret | Phase 1 | Anyone who knows a key can read its stored URLs from Apprise (`GET /get/{KEY}`); the API returns it as §7 specifies. Make it write-only like `urls` if that is judged too weak. |
| `GET /notifications/{id}`; API listing of `destination_files` | Phase 1 | Not in §7; the list endpoints cover the UI. `syncer.Store` exports the queries for when an endpoint is wanted. |
| Job detail: log level filter and log download | Phase 1 | Not in §10; the log view shows every level with colour and follows new lines. |
| Code splitting of the UI bundle | Phase 1 | 435 kB (131 kB gzip) is fine for a LAN-served app; revisit if it grows. |
| "Scan all sources" and bulk actions in Library | Phase 1 | Not in §10; each source has its own Scan. |
| Plex test gaps in the Docker suite | Phase 1 | The real-PMS test covers section listing, a path mapping, importing a location as a source and syncing it, and the backup/restore. Not covered with a real PMS: a claimed server and the `X-Plex-Token` path (the test PMS is unclaimed, so no token is sent; the token handling is tested against `plextest`), a stopped or crashed PMS (the `immutable=1` path), a TV section with several locations, a container kill during a Plex backup, and a check that PMS logged no errors (an unclaimed, offline PMS logs unrelated errors). The spike, the plexdb unit tests and its crash matrix cover the backup paths. |
| actionlint on the workflows | Phase 1 | Not installed locally; the workflow YAML is only parsed. |
| Nested FUSE mount that fails over a FUSE parent | Phase 1 | FUSE has no stable inode to compare, so a failed nested FUSE mount whose bare mountpoint holds files is scanned as the source (the empty-root and f_type checks still catch the common cases). Checking the FUSE subtype in mountinfo would close it. |
| Scheduler firing between an integration's delete check and its schedule removal | Phase 1 | The in-memory scheduler can still enqueue a Plex backup in that window; the runner then records the version without the integration link (it is not lost). Closing it needs the scheduler to hold off while deleting. |
| Plex token in the backup's `Preferences.xml` | Phase 1 | Every Plex DB version stores `Preferences.xml`, which holds `PlexOnlineToken`, in cleartext at the destination. Mode 0600 is not enforced on an SMB share without POSIX extensions (file modes come from the mount options), so anyone who can read the share may read the token. Documented in the README; the Settings → Plex backup help does not say it yet. Plan: a per-integration option to skip `Preferences.xml`, or to seal it with the keyring (restorable only with `bunkarr.key`, through Bunkarr). |
| Backup of Bunkarr's own database | Phase 1 | `/config/bunkarr.db` (records, schedules, settings) is not backed up by Bunkarr. A restore does not need it (plain files, `links.tsv`, Plex versions with manifests), but after losing `/config` a re-attached destination is adopted or re-copied file by file, and what is in `.bunkarr/retention` is no longer recorded (never expired). Plan: an online SQLite backup to a destination like the Plex DB (`bunkarr.key` stays with the user). |
| Test of the verify dry run | Phase 1 | The verify runner's dry run (plans the files it would check, checks nothing) has no dedicated test; the sync, retention and Plex backup dry runs have. It is reachable from the API and System → Tasks → Preview. |
| Resumed-job presentation | Phase 1 | Found while taking the screenshots: a job resumed after a clean restart has its trigger rewritten to "resume" (the original "manual"/"schedule" is lost), its header duration includes the pause while the Duration stat counts only the last attempt, and a resumed sync finishes with an empty per-source table. Data is unaffected. |
| Phone layout of list pages | Phase 1 | On a 390 px screen the Queue, History, Library, Destinations and Tasks tables scroll sideways and the Queue hides progress and speed; job pages fit. Needs responsive card layouts. |
| Mass-change guard percentage base | Phase 1 | The guard's percentage is computed against the source's live files after the deletion ("10 % of 39" when 26 of 65 vanished), which holds earlier than intended; the message should use the count before the change. Safe direction. |
| "Last run" for jobs started by hand | Phase 1 | System → Tasks shows a schedule's last run only for scheduled runs and Run now; a sync started from Destinations → Sync now does not update it. |
| Occasional EFAULT writing a large file to CIFS under Docker Desktop | Phase 1 | Seen once (562 MiB file, Docker Desktop's 7.0.12-linuxkit kernel, Samba share): the item failed with "bad address" and the next sync copied it. To be checked on a real Unraid + UNAS mount; the item-level failure and retry work as designed. |
